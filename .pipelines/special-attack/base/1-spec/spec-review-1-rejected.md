## Summary

The spec is strong and, for 12 of its 13 requirements, faithfully and verifiably mirrors the shipped "Who's Faster?"/Speeds model page: routing, discoverability, the section-selector shell, the head-to-head quiz (reveal animation, reduced-motion fallback, streak/tie/game-over/restart mechanics), the sortable-searchable table, and the "existing `spAttack` data only" boundary all re-executed cleanly against the codebase, and the open reuse-vs-generalize direction is correctly deferred to design (OOS 5). One requirement fails: Requirement 12 (and its acceptance criterion) describe an insufficient-data behavior that contradicts the model it claims to mirror, and that behavior was never recorded in the research it cites for grounding. Because this is a testable requirement whose stated behavior would lead two implementers to different builds, the spec is rejected for this single, fixable issue.

## Issues

### Issue 1: Requirement 12's insufficient-data behavior contradicts the model and is ungrounded in the research

**What's wrong:** Requirement 12 states the page "shows a graceful 'not enough Pokémon' message **in place of the quiz**," and its acceptance criterion says "a 'not enough Pokémon' message is shown **instead of the quiz**." Both wordings imply the hero, section selector, and table still render and only the quiz region is swapped for a message. The model page does something different: when `pokemons.length < 2`, `src/pages/speeds.ts:62-64` returns early with the whole page replaced by a single paragraph — `<main><p>Not enough Pokemon loaded.</p></main>` — so hero, selector, and table are all absent. The requirement claims to be "mirroring the model page" (research consolidated Req 12), but it describes a different observable outcome than the model actually produces.

Separately, the grounding chain is broken: the research cites "(R1: shell)" for Requirement 12, but R1's "Page shell / section visibility" paragraph documents only the `currentSection` hidden-bindings, not the `length < 2` early return. A `grep` of `spec-research.md` finds the edge case mentioned only in the consolidated requirement itself (line 99) — no R1/R2 research finding or evidence bullet records a check of the model's insufficient-data behavior. So the "mirroring the model page" claim rests on a check that was never performed.

**Where:** `spec.md` Requirement 12 (line 22) and the corresponding acceptance criterion (line 46); `spec-research.md` consolidated Requirement 12 (line 99). Model behavior: `src/pages/speeds.ts:62-64`.

**Suggestion:** Adjudicate one of two ways and align the spec, its AC, and the research grounding to match:
- (a) If the intent is a true mirror, restate Requirement 12 and its AC as the model's actual behavior — when fewer than two Pokémon are loaded, the page renders only a graceful "not enough Pokémon" message (no hero, selector, or table) and does not error — and add a research finding (with the `src/pages/speeds.ts:62-64` evidence) that records this model behavior so the requirement is grounded.
- (b) If the intent is deliberately to improve on the model by preserving the hero/selector/table and replacing only the quiz, keep the current wording but record it as an intentional, justified divergence from the model rather than as "mirroring," and ground it accordingly.

**Why it matters:** This is a testable requirement whose stated behavior contradicts the model it claims to mirror, so a downstream implementer told to "mirror Speeds" and an implementer coding to the acceptance criterion would build observably different pages (bare message vs. hero+selector+table+message). It fails the fidelity gate that two implementers reading independently build the same understanding, and it leaves a load-bearing claim about the model's behavior asserted without any recorded check behind it.
