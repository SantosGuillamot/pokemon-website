# Design Research: Special Attack Comparison Page

## Research

### R1: Structure of the Speeds page/store, shared components, namespace mechanics, build wiring

Source: design-researcher investigation (research request 1), grounded file:line in the worktree.

**Client store `src/client/stores/pages/speeds.ts`.**
- Registered once: `store("pokemon/speeds", {...})` at line 125. Side-effect imports of shared stores: `@pokemon-website/stores/pokemons` (l.3), `../data-table.js` (l.4), named imports from `quiz-utils` (l.5-13).
- Stat coupling to `.speed` is exactly THREE plain property reads, all in scope: l.63 `Math.round(animationProgress * pokemon.speed)` (count-up target in `getDisplayedSpeed`), l.238 `pokemonA.speed === pokemonB.speed` (tie), l.241 `pokemonA.speed > pokemonB.speed ? 0 : 1` (correctness). Everything else matching "speed" is either the namespace string, identifier names, or the numeric guess-speed game (`speedGuess`, `correctSpeed`, `submitGuessSpeed`, l.257 `correctSpeed = pokemon.speed`, etc.) — that whole numeric game is out of scope (spec Out-of-Scope #1).
- Reveal animation + streak/game-over are fully stat-agnostic: `revealAnswer` (l.66-123) touches only `animationProgress`/`streak`/`finalStreak`/`quizState`/`correctAnswer`; it holds the `prefers-reduced-motion` branch (l.74-94, `matchMedia("(prefers-reduced-motion: reduce)")` jumps `animationProgress=1`) and the cubic ease-out rAF count-up (l.96-122). `revealAnswer` and `getDisplayedSpeed` are module-level helpers local to `speeds.ts` (l.34-123), NOT in shared `quiz-utils`.
- Data flow (three paths): (a) quiz INITIAL pair is server-seeded — page runs `pickTwo(pokemons)` server-side and passes `randomPokemons=[{dexNumber,formName}]` into context (speeds.ts:119-127); store reads `context.randomPokemons`. (b) quiz stat VALUES + subsequent pairs are client-side — store calls `pokemonState.getPokemon(dex,form)`/`getRandomPokemons(2)` against the shared `"pokemon"` store (populated server-side into the `#wp-interactivity-data` JSON blob, Layout.ts:31); the pair carries only `{dexNumber,formName}` in context and `.speed` is looked up client-side. (c) table rows are server-built and static — page maps ALL pokemons to `speedRows` (speeds.ts:75-80) passed as `DataTable({rows})`, serialized into the data-table region's context; the table does NOT read the client pokemon store.

**Page component `src/pages/speeds.ts`.** Plain zero-arg `WhosFasterPage()` (l.55), default export, NOT parameterized — all strings/stat inline. Reads server data via `getServerData()` (l.58-61); early return confirmed: `if (pokemons.length < 2) return html\`<main><p>Not enough Pokemon loaded.</p></main>\`` (l.62-64). Namespace referenced once in HTML: `data-wp-interactive="pokemon/speeds"` + `data-wp-context='{"currentSection": null}'` on wrapper (l.93). Two page-local presentational helpers `SpeedRevealOverlay` (l.14-33) and `SpeedPokemonCard` (l.35-53) inline the reveal overlay + card button, binding `state.displayedSpeed`/`actions.guessSpeed`.

**Interactivity API namespace mechanics (verified in package source `node_modules/@wordpress/interactivity/build-module/store.mjs`).** Stores live in a `Map` keyed by namespace string (`var stores = new Map()`, l.6). `store(namespace, {...})` creates a fresh proxified store if the namespace is absent, else `deepMerge`s into the existing one (l.22-55). So the `data-wp-interactive="X"` string in HTML and the `store("X")`/`getContext("X")` string in JS are the SAME single coupling key. Two DIFFERENT namespaces = two fully independent singletons that coexist cleanly, no shared/global leak. SAME namespace registered twice = merged into one shared store. Project stores are public (no `lock`). This matters under client-side navigation: Layout tags page scripts `loadOnClientNavigation:true` (Layout.ts:48-51) and body is `data-wp-router-region="full-page-csn"` (Layout.ts:53), so navigating /speeds↔/special-attack keeps both store modules alive in one runtime — a DISTINCT namespace `pokemon/special-attack` is collision-free; reusing `pokemon/speeds` for a second page would MERGE state (the one thing to avoid). Precedent: `pokemon/data-table` is ONE singleton (data-table.ts:19) driving multiple independent regions purely because all per-region state is in `data-wp-context`.

**Shared components — already extracted, prop-driven, reusable as-is:** `DataTable` (src/components/DataTable.ts) fully config-driven (`columns[]`, `rows[]`, `sortColumn`/`sortDirection`, `searchMode:"filter"|"scroll"`, `caption`, `maxHeight`, `searchPlaceholder`); proven by two callers with different column sets (speeds.ts:196-209; MetaPokemonsSection.ts:10-62, which already uses `{key:"spAttack", label:"SpA", sortable:true}` at l.48). Its client logic (data-table.ts) is stat-agnostic. `SectionCard` (props title/description/sectionId), `Hero` (props title/description/image/imageBg), `QuizStatus` (renders "Streak: N" / "GAME OVER / Final streak / Try again" bound to `context.streak`/`context.finalStreak`/`state.isIncorrect`; zero stat coupling), and its wrapper `QuizSection` (props sectionId/quizContext/watchCallback/restartAction/children) — all generic, reuse as-is. Only inline stat-named surfaces are `SpeedRevealOverlay`/`SpeedPokemonCard` (page-local in speeds.ts) and the speed-NAMED but cosmetic CSS classes `.speed-overlay-bg/-correct/-incorrect`, `.speed-correct/-incorrect`, `.speed-pokemon-btn` (src/styles/input.css:510-570).

**Build wiring `scripts/build.ts`.** Client stores are bundled via an explicit hardcoded `entryPoints` array (l.5-16); esbuild outputs each to `public/js/<path-relative-to-src/client>` (outbase `src/client`, outdir `public/js`). `src/client/stores/pages/speeds.ts` (array l.12) → `public/js/stores/pages/speeds.js`, matching the route entry's `scripts:["/js/stores/pages/speeds.js"]` (routes/index.ts:37), injected by Layout as `<script type=module>`. NOT glob/auto-discovered — a new page store MUST be added to the entryPoints array or its `scripts` path 404s. Shared stores (interactivity/router/nav/pokemons) load unconditionally via Layout (l.47-50); page store is per-route.

**Wiring points for a mirrored page (from R1):** (a) `src/pages/special-attack.ts`, (b) route entry in `src/routes/index.ts` with `scripts:["/js/stores/pages/special-attack.js"]`, (c) `src/client/stores/pages/special-attack.ts`, (d) that path added to `scripts/build.ts` entryPoints, (e) nav `GAME_LINKS` entry (Nav.ts:6-11), (f) homepage `GAMES` card (home.ts:14-43).

### R2: Store/page/CSS internals for the fork sub-decisions

Source: design-researcher investigation (research request 2), verbatim bodies from the worktree.

**Reveal logic.** `revealAnswer` (speeds store l.66-123) is fully stat-agnostic — it touches only `quizState`/`animationProgress`/`streak`/`finalStreak`, holds the `prefers-reduced-motion` branch (`window.matchMedia("(prefers-reduced-motion: reduce)")` → jump `animationProgress=1`) and the cubic ease-out rAF count-up (`1 - (1 - progress) ** 3`), and calls an `onNextRound` callback. `getDisplayedSpeed` (l.53-64) is NOT stat-agnostic: it reads `pokemon.speed` directly via `pokemonState.getPokemon(dex,form)`. Helpers `toQuizPokemon`/`randomize`/`resetQuizState` (l.34-51) are stat-agnostic (operate on `{dexNumber,formName}` and context fields).

**`quiz-utils` (`src/client/stores/quiz-utils.ts`) is genuinely shared.** Full export set: type `QuizPokemon`; fns `randomizeSingle`, `syncPokemonContext`, `isWaiting(namespace)`, `isIncorrect(namespace)`; re-exports `isCurrentSection`, `selectSection` (from section-utils). Every helper is namespace/stat-agnostic (takes a namespace string or generic context; none reads a specific stat). Imported today by `src/client/stores/pages/speeds.ts:13` AND `src/client/stores/pages/types.ts:17` (and the Layout importmap alias). So editing quiz-utils touches a module the Types page also loads. `revealAnswer`/`getDisplayedSpeed` are NOT in quiz-utils — they live only in speeds.ts; Types does not use them. Therefore a fork that copies them into the new store touches no shared code at all; extracting `revealAnswer` into quiz-utils would fit its abstraction but would edit a Types-loaded module.

**Page-local presentational helpers (src/pages/speeds.ts).** `SpeedRevealOverlay` (l.14-33) is already parameterized on binding strings (`textBinding`/`correctBinding`/`incorrectBinding`); its only stat-specific bits are `aria-label="Speed stat"` and the `.speed-*` class names. `SpeedPokemonCard` (l.35-53) stat-specific bits: `aria-label="Select ... as faster"`, `data-wp-on--click="actions.guessSpeed"`, and the overlay bindings `state.displayedSpeed`/`state.isGuessedCorrect`/`state.isGuessedIncorrect` (the latter two are stat-neutral). Stat-neutral and reused verbatim: `pokemonIndex`, the `pokemon::`-namespaced context, `callbacks.updateContext`, `state.isWaiting`, and `PokemonCard()`.

**Head-to-head `QuizSection` invocation (speeds.ts l.119-138).** Props: `sectionId:"whos-faster"`, `sectionContext:{randomPokemons}`, `quizContext:{...defaultQuizContext(), randomPokemons, animationProgress:0, guessedIndex:null}`, `watchCallback:"callbacks.storeAnswer"`, `restartAction:"actions.restart"`. `defaultQuizContext()` (src/utils/quiz.ts) = `{streak:0, quizState:"waiting", finalStreak:0}`. Only stat-specific child string is the `<h3 class="sr-only">Which Pokemon is faster?</h3>`. Server seeds the initial pair via `pickTwo(pokemons)` (l.65) → `randomPokemons=[{dexNumber,formName},{dexNumber,formName}]` (no stat value; the `.speed`/`.spAttack` lookup is client-side). `pickTwo` (src/utils/array.ts:15-22) returns two DISTINCT random elements, requires length>=2 (guaranteed by the `<2` early return) → Requirement 5 ("two distinct") satisfied by reuse.

**CSS (`src/styles/input.css:510-570`).** The `.speed-overlay-bg/-correct/-incorrect`, `.speed-correct/-incorrect`, `.speed-pokemon-btn` rules use only generic design tokens (`--color-success`/`--color-error`/`--color-black`/`--color-fog`/`--color-white`/`--shadow-card-pressed`) — nothing speed-domain-specific; names are speed-NAMED but styling is generic reveal/hover-press feedback. Grep of the 6 class names across `src`: referenced ONLY by their definitions in input.css and by `src/pages/speeds.ts` (l.20,23,24,29,30,38) — nothing else (not Types, not any component). CSS is a single global bundle: `build:css` = `tailwindcss -i src/styles/input.css -o public/css/app.css`; `Layout.ts:30` links `/css/app.css` on every page. So both pages already ship all these classes; reusing `.speed-*` on the new page is safe and cannot affect any other page.

## Topics

### Topic: Reuse vs. generalize the Speeds page/store/components (CENTRAL)

- **Spec link:** Requirements 1-13; Out of Scope 5 (existing pages observably unchanged); the intent explicitly left reuse-vs-generalize open.
- **Options:**
  1. **Fork** — new page `src/pages/special-attack.ts` + new client store `src/client/stores/pages/special-attack.ts` under a distinct namespace `pokemon/special-attack`, carrying only the head-to-head quiz + section selector + table (dropping the numeric guess-speed game and the dead moves-priority stub); reads swapped `.speed` → `.spAttack`; all shared components reused as-is.
  2. **Parameterize the store** — a factory `store` keyed by a `statKey: "speed"|"spAttack"`, both pages calling it, editing the shipped `pokemon/speeds` store to consume the factory.
  3. **Generalize the whole page** — a shared "stat comparison page" builder producing both pages from a stat descriptor.
- **Trade-offs:** The heavy generic logic (Hero, SectionCard, QuizSection, QuizStatus, DataTable + its `pokemon/data-table` store, reveal animation, streak/game-over) already lives in shared modules or is stat-agnostic; genuine stat coupling is 3 property reads in the store plus copy strings and 2 page-local presentational helpers. So DRY savings from (2)/(3) are small (~3 lines + thin glue), while both edit the shipped `pokemon/speeds` surfaces, creating an observable-regression risk on `/speeds` (Requirement 13) that must be re-verified. (2) is further complicated because the guess-speed members are speeds-only and out of scope here, so a clean stat factory must special-case them. (3) is speculative: spec-research R2 confirms no roadmap for further per-stat pages — Speeds is the sole precedent — so a page abstraction would have exactly one-and-a-half users.
- **Decision (primary axis):** **Fork (Option 1).** New page + new store under distinct namespace `pokemon/special-attack`; all shared components (Hero, SectionCard, QuizSection, QuizStatus, DataTable + `pokemon/data-table`) reused as-is with no modification. The finer sub-decisions (whether to extract the stat-agnostic reveal helper into shared `quiz-utils`, how to handle the page-local presentational helpers, and CSS class naming) are decided in their own topics below.
- **Rationale:**
  - Strongest guarantee for Requirement 13 / Out-of-Scope 5: the fork touches no existing page's rendering or store, so `/speeds` (and every other page) is observably unchanged by construction; the only edits to existing files are additive discoverability entries (nav array, homepage array) and the build entryPoints array.
  - The numeric guess-speed exclusion (Out-of-Scope 1) is realized trivially — the members are simply not carried into the new store — whereas under (2) the factory would have to special-case speeds-only members.
  - Namespaces are independent singletons (verified in `@wordpress/interactivity` package source): a distinct `pokemon/special-attack` namespace is collision-free even under client-side navigation, where both `/speeds` and `/special-attack` store modules stay alive in one runtime; reusing `pokemon/speeds` would merge state and is the one thing avoided.
  - The DRY cost of forking is small and bounded because all the substantial generic logic is already extracted into shared, prop-driven components and stores — so "most coherent code" favors two small self-contained page stores over a speculative abstraction with one-and-a-half users.
- **Evidence:**
  - Stat coupling in the store is 3 property reads (l.63, 238, 241) and the reveal/streak logic is stat-agnostic — R1 (design-researcher grep of `src/client/stores/pages/speeds.ts`).
  - Shared components are already generic and reusable as-is (DataTable proven by two callers with different column sets incl. MetaPokemonsSection's `spAttack`/`SpA` column) — R1.
  - Distinct namespaces are independent Map-keyed singletons; same namespace merges — R1 (`node_modules/@wordpress/interactivity/build-module/store.mjs:6,22-55`), plus CSN keeps both modules alive (Layout.ts:48-53).
  - No roadmap for further per-stat pages; Speeds is the sole precedent — spec-research R2.
  - A new store must be added to the explicit `scripts/build.ts` entryPoints array (not auto-discovered) — R1.

### Topic: Fork sub-decisions — what to share vs. duplicate (guiding principle + A/B/C)

- **Spec link:** Requirement 13 / Out-of-Scope 5 (existing pages observably unchanged; reuse-vs-generalize is a design decision); Requirements 5, 6, 7, 9 (quiz mechanics realized by the copied store logic).
- **Guiding principle (applied uniformly below):** Share/generalize only where the shared thing carries substantial, behavior-bearing logic AND the codebase already has a shared home for it; do NOT reach into existing observable-page source to refactor stable code or improve cosmetics. Requirement 13 is the spec's strongest, acceptance-criterion-level constraint, so the fork is designed to touch **no existing observable page's rendering, store, styling, or shared runtime module** — the only edits to existing files are (1) route registration in `src/routes/index.ts`, (2) the build entryPoint in `scripts/build.ts` (both mandatory to ship any page), and (3) the additive `GAME_LINKS` nav entry and `GAMES` homepage card (Requirement 2). Everything else is new files.

- **A. Reveal animation + stat reader (store):** DUPLICATE `revealAnswer` and `getDisplayed<Stat>` into the new store (the latter renamed and reading `.spAttack`); do NOT extract into shared `quiz-utils`.
  - **Alternative considered:** extract the stat-agnostic `revealAnswer` into `quiz-utils` (it fits the module's abstraction) and have both stores import it; keep `getDisplayed<Stat>` local. Rejected for this feature: `quiz-utils` is loaded by the Types page store too, so the extraction edits a shared runtime module and adds a re-verification obligation for both `/speeds` and `/types` — a real (if low) regression surface — to remove one duplicated function. `revealAnswer` is stable, shipped, and not under active development, so duplication carries little drift risk here. The extraction is behavior-preserving and spec-permitted and remains a safe optional follow-up; it is deferred rather than bundled into a feature whose defining constraint is "no regressions elsewhere."
  - **Trade-off accepted:** ~58 lines of animation logic (incl. the reduced-motion branch, Requirement 6) and the ~12-line stat reader are duplicated. Logged as a residual with the DRY follow-up (see Risks).
- **B. Page-local presentational helpers (`SpeedRevealOverlay`/`SpeedPokemonCard`):** DUPLICATE into the new page as `SpAttack*` equivalents, renaming the stat-specific strings/bindings (`aria-label` "Speed stat"→"Special Attack stat" and "…as faster"→"…as having higher Special Attack"; `actions.guessSpeed`→`actions.guessSpAttack`; `state.displayedSpeed`→`state.displayedSpAttack`; `isGuessedCorrect/Incorrect` and all other bindings reused verbatim).
  - **Alternative considered:** extract a shared `RevealOverlay`/`QuizChoiceCard` component parameterized on label+action+bindings. Rejected: these are ~20-line presentational markup helpers with no substantial behavior; parameterizing every stat-specific string/binding yields a helper about as complex as two copies, and sharing would require editing `speeds.ts`. Keeping them page-local matches the existing pattern and keeps each page self-describing.
- **C. Reveal/hover CSS classes:** REUSE the existing `.speed-*` classes as-is on the new page (single global bundle already ships them; values are generic design tokens; grep confirms they are referenced only by the Speeds page, so reuse cannot affect any other page).
  - **Alternatives considered:** (i) add generic aliases (`.quiz-reveal-*`, `.quiz-choice-btn`) for the new page — rejected as it creates two class-name sets for identical styling (which name is canonical?); (ii) rename `.speed-*`→generic in both `input.css` and `speeds.ts` markup — rejected because it edits the rendered markup of `/speeds` purely for a cosmetic naming gain, against the guiding principle.
  - **Trade-off accepted:** the new page's markup will carry `speed`-named classes on a Special Attack page — a cosmetic, user-invisible naming mismatch. Logged as a residual with an optional future rename-to-generic (see Risks).
- **Rationale (why this cut is coherent, not just conservative):** the substantial generic logic (Hero, SectionCard, QuizSection, QuizStatus, DataTable + its store, `pickTwo`, `defaultQuizContext`, section/quiz-state utils) is already shared and reused as-is; what remains stat-coupled is thin. Given that, the most coherent *whole* is a self-contained new page that adds a feature without reaching into shipped pages — the duplication is bounded, stable, and self-describing, and the two deferred generalizations (revealAnswer extraction, CSS rename) are recorded as safe, optional follow-ups rather than silently dropped.
- **Evidence:**
  - `revealAnswer` is stat-agnostic; `getDisplayed*` reads the stat directly; `quiz-utils` is imported by both speeds and types stores and does NOT contain the reveal helpers — R2.
  - `.speed-*` classes use only generic tokens and are referenced solely by the Speeds page; CSS is one global bundle loaded on every page — R2.
  - `pickTwo` returns two distinct elements; the quiz section, `defaultQuizContext`, and initial-pair seeding are stat-agnostic and copy verbatim — R2.

### Topic: Naming, URL, labels, copy, and discoverability entries

- **Spec link:** Requirements 1 (URL), 2 (nav + homepage card), 3 (hero title/description), 10 (table stat column label).
- **Options / decisions (all copy strings are proposed defaults grounded in codebase convention; owner-adjustable per spec preamble, not load-bearing):**
  - **URL path:** `/special-attack` — mirrors the `/speeds` single-segment stat path. (Requirement 1)
  - **Nav label (`GAME_LINKS`):** `"SPECIAL ATTACK"` — uppercase stat word, mirroring `"SPEEDS"` (Nav.ts:6-11 convention: stat word uppercased). (Requirement 2)
  - **Hero title:** `"Special Attack"` (literal), **not** a coined "Who's ___?" question. Speeds uses a catchy "Who's Faster?" because Speed has a natural single-word comparative ("faster"); Special Attack has none, and spec-research R2 flags that "Who Hits Harder?"/"Who's Stronger?" both risk conflating with the separate physical Attack stat and are unverified coinages. A literal title matches the established prose convention ("Special Attack" appears in roles.ts:30, CONTENT.md:65) and avoids ambiguity. (Requirement 3)
  - **Hero description:** a short line in the Speeds mold — guess which Pokémon has the higher Special Attack, ties are safe, one wrong answer ends the streak. (Requirement 3)
  - **Homepage card title:** `"Special Attack"` (consistent with hero) with a short description ("Test your Special Attack knowledge!" style, mirroring the Speeds card copy). (Requirement 2)
  - **Homepage card icon:** `Zap` (named import from `lucide-static`, set as the `icon` in the `GAMES` entry). Confirmed a real export (R3) and unused by the other four game cards; reads as an energy/special blast and is visually distinct from `Swords` (the physical-attack-flavored "Will It KO?" card). `Sparkles`/`Flame`/`Wand2` are equally valid owner-adjustable alternatives. (Requirement 2)
  - **Table stat column label:** `"Special Attack"` (full word), mirroring the Speeds table's full-word `"Speed"` header (speeds.ts:200). Alternative `"SpA"` (the abbreviated convention in multi-stat tables — design-system.ts:543, MetaPokemonsSection.ts:48) is rejected here because the design principle for this page is to mirror the single-stat Speeds table, which spells the stat out; the abbreviation earns its place only in dense multi-stat tables. (Requirement 10)
- **Rationale:** Each choice mirrors the corresponding Speeds surface's own convention, so the new page reads as a sibling of the model page; where Speeds' choice does not transfer (the "Who's Faster?" pun), the literal stat name is the unambiguous, convention-backed default.
- **Evidence:**
  - Nav uppercases the stat word; homepage card uses a lucide icon — spec-research R1 (Nav.ts:6-11, home.ts:14-43).
  - "Special Attack" prose and "SpA" abbreviation are the two established naming conventions; no "Who's ___?" analogue exists for SpA — spec-research R2.
  - Speeds table column header is the full word "Speed" — spec-research R1 (speeds.ts:200).

### Topic: Interfaces and data flow

- **Spec link:** Requirements 1 (SSR route), 5-9 (quiz), 10 (table), 11 (existing data only).
- **Route / SSR:** Hono `GET /special-attack` handled by the shared loop in `routes/index.ts` → `resetServerState()`, `await loadTypes()`, `await loadPokemons()`, then `Layout({ title:"Special Attack", scripts:["/js/stores/pages/special-attack.js"], children: SpecialAttackPage() })`. No client fetch is needed for first paint (data is in the SSR HTML and the `#wp-interactivity-data` blob) — satisfies Requirement 1's acceptance criterion.
- **Page data prep:** `getServerData()` → `pokemons`. If `pokemons.length < 2` → return the bare `<main><p>Not enough Pokemon loaded.</p></main>` (Requirement 12). Else: build `spAttackRows = pokemons.map(p => ({ id, sprite: imageUrl, name: capitalize(p.name), spAttack: p.spAttack }))`; `const [a,b] = pickTwo(pokemons)` → `randomPokemons = [{dexNumber,formName},{dexNumber,formName}]` (no stat value carried).
- **Interactive region:** wrapper `<div data-wp-interactive="pokemon/special-attack" data-wp-context='{"currentSection": null}'>`. The `QuizSection` seeds its own `data-wp-context` with `quizContext = {...defaultQuizContext(), randomPokemons, animationProgress:0, guessedIndex:null}` and `watchCallback:"callbacks.storeAnswer"`, `restartAction:"actions.restart"`.
- **Section visibility (Requirement 4):** `currentSection` starts `null`, so only hero + selector cards show on load; each `SectionCard` click calls `actions.selectSection` (from shared section-utils) to set `currentSection`; both the `QuizSection` and the table's section wrapper bind `data-wp-bind--hidden="!state.isCurrentSection"` (`isCurrentSection` compares `currentSection` to the section id), giving exactly-one-visible behavior. The head-to-head `QuizStatus` renders "Streak: N" (bound to `context.streak`) during play and the "GAME OVER / Final streak / Try again" state on a loss (Requirements 9, 7). Mechanism inherited unchanged from Speeds (spec-research R1, section-utils.ts:3-8).
- **Client store data flow:** reads `context.randomPokemons` (the seeded pair, `{dexNumber,formName}` only); resolves each Pokémon's `.spAttack` client-side via the shared `pokemon` store's `getPokemon(dex,form)`; `state.displayedSpAttack` = `getDisplayedSpAttack(pokemonData, context.animationProgress)` drives the count-up; `callbacks.storeAnswer` sets `context.correctAnswer` from `a.spAttack === b.spAttack ? "tie" : (a.spAttack > b.spAttack ? 0 : 1)`; `actions.guessSpAttack` marks correct/incorrect vs `guessedIndex` and calls `revealAnswer(context, isCorrect, () => randomize(context))`. Subsequent pairs come from `pokemonState.getRandomPokemons(2)` client-side.
- **DataTable interface:** `DataTable({ columns, rows: spAttackRows, sortColumn:"spAttack", sortDirection:"desc", searchMode:"scroll", caption:"Pokemon sorted by special attack", maxHeight:"70vh", searchPlaceholder:"Search Pokemon..." })` where `columns = [ sprite (image render, alt=name), { key:"name", label:"Name", sortable:true, searchable:true }, { key:"spAttack", label:"Special Attack", sortable:true } ]`. Runs in the shared `pokemon/data-table` region; rows are static SSR data. Satisfies Requirement 10 (default sort spAttack desc; sort by name or spAttack; `searchMode:"scroll"` scrolls-to+highlights rather than filtering).
- **Message/data shapes:** `randomPokemons: { dexNumber:number, formName:string|null }[]`; table row: `{ id:string|number, sprite:string, name:string, spAttack:number }`.

### Topic: Post-change coherence

- **Spec link:** Requirement 13.
- **Finding:** The fork is purely additive — it introduces a parallel page and store and reuses shared components that already have ≥2 callers, so it narrows no surviving code's contract and strands no generality. No existing function's body, name, contract, docs, or tests are made false. The two places where the design consciously declines to generalize (`revealAnswer` duplication; `.speed-*` class names on the new page) are recorded residuals (see Risks), not incoherences in shipped code. Existing observable pages are untouched, so Requirement 13 holds by construction.

### Topic: Dependencies

- **Spec link:** Requirement 11 (no new data source/schema); 6 (reduced motion via platform API).
- **Finding:** No new dependencies. Reuses existing: `@wordpress/interactivity` (`store`/`getContext`, `data-wp-*` directives, `matchMedia`-based reduced-motion, client-side router), Hono (routing), the Drizzle-inferred `Pokemon` type and existing read-only `loadPokemons`/`loadTypes` (no schema/query/API change), `lucide-static` (homepage card icon), `esbuild` (bundling), `tailwindcss` (single global CSS bundle). `spAttack` already exists in the server data the page consumes (spec-research R1) — Requirement 11 satisfied with zero backend work.

### Topic: Failure modes and observability

- **Spec link:** Requirements 6, 8, 12.
- **Findings:**
  - **Insufficient data (<2 Pokémon):** whole-page early return renders only the bare "Not enough Pokemon loaded." message; hero/selector/quiz/table do not render and nothing throws (Requirement 12). `pickTwo`'s length>=2 precondition is guarded by this early return.
  - **Reduced motion:** `revealAnswer` checks `matchMedia("(prefers-reduced-motion: reduce)")` and jumps `animationProgress=1`, showing final values instantly (Requirement 6).
  - **Ties:** `storeAnswer` yields `correctAnswer:"tie"`, making either selection correct (Requirement 8).
  - **Client lookup miss:** if `getPokemon` returns null, `getDisplayedSpAttack` returns 0 and `randomize` bails when fewer than 2 are available — graceful, no throw.
  - **Observability:** the model page adds no server logging/telemetry, and this design adds none — client-side failures degrade gracefully (zeroed values, no advance). No new observability surface is introduced; consistent with precedent. (Noted as a deliberate non-addition, not a gap.)

## Risks

- **R-1 (accepted residual — duplication of reveal logic).** `revealAnswer` (~58 lines, incl. the Requirement-6 reduced-motion branch) and the small stat reader are duplicated across the Speeds and Special Attack stores. Impact: a future change to the reveal animation must be applied in both. Why deferral is safe: the code is stable and shipped, and a behavior-preserving extraction into shared `quiz-utils` is available at any time. Resolution/observation: an optional follow-up refactor extracting `revealAnswer` into `quiz-utils`, verified by exercising the reveal on `/speeds`, `/types`, and `/special-attack`.
- **R-2 (accepted residual — `.speed-*` class names on a Special Attack page).** The new page's markup carries `speed`-named classes. Impact: cosmetic/readability only; user-invisible and functionally correct (values are generic tokens; grep confirms no cross-page coupling). Why safe: no behavior depends on the names. Resolution: optional future rename of `.speed-*`→generic (`.quiz-reveal-*`/`.quiz-choice-btn`) across `input.css` + `speeds.ts` markup.
- **R-3 (risk to flag to the build phase — namespace must be distinct).** Requirement 13 depends on the new store registering a DISTINCT Interactivity namespace `pokemon/special-attack`. Because page scripts stay alive across client-side navigation, reusing `pokemon/speeds` would MERGE the two pages' store state (verified in package source, R1) and corrupt both. Mitigation: the design specifies `pokemon/special-attack`; the build phase must not reuse the Speeds namespace, and the `data-wp-interactive` string in the page HTML must match the `store()` namespace exactly.
